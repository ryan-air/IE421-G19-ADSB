# Fall 2025 Baseline: Findings

The full tables are in [report.md](report.md), generated by [`bench/legacy/`](../../legacy/) (method and caveats in its README). Each run fed 120 s of synthetic traffic in real time to the **unmodified** Fall 2025 pipeline: readsb → Python streamer → Postgres → Node API → map polling every 2 s. The sweep covered 50 to 6,000 aircraft (200 to 24,000 frames per second).

> **Machine:** Apple M2 laptop, Docker Desktop Linux VM, local Postgres (no Supabase network hop). Latencies are therefore a lower bound on the deployed system. CPU use and the load ceiling must be re-measured on the benchmark host. The latency *structure* comes from the code's design and does not depend on the machine.

## Headline numbers (range across 50–6,000 aircraft)

| Measure | Fall 2025 system |
|---|---|
| Frame received → visible on the map | **1.07–1.57 s** median, 2.05–2.88 s p99 |
| Positions that ever reach the database | **17%** (5 of every 6 position reports are discarded) |
| Age of the position the map shows | **1.8–2.2 s** median, about 12.5 s p99 |
| Distance between the map and the aircraft's real position (in the browser) | **454–517 m** median, about 2.6–2.7 km p99 |
| Correctness | Every shown position matched a real transmitted position (0 unmatched) |

For context, the new C++ pipeline takes the same frames from received to track state updated in **0.4–0.8 µs** median and 7–22 µs p99, keeping every position. Its publisher, gateway and map are not built yet, so that is not yet an end-to-end comparison.

## What the measurements show

1. **The latency is designed in.** Almost all of it comes from three waits in the code, not from slow computation:
   - the streamer's 1 s batch flush (or 100 buffered aircraft, whichever comes first);
   - the database round trip;
   - the map's 2 s poll, which alone adds about 1 s on average and 2 s at worst.

   The database is reached in 66–570 ms median, and the browser poll then adds about another second on average.
2. **Load shortens latency.** The database median falls from 570 ms with 50 aircraft to 66 ms with 6,000. That is because the batch of 100 aircraft fills sooner, not because anything got faster. readsb behaves the same way: its output buffer flushes at 1,280 bytes or 50 ms, so its median drops from 27 ms to 2 ms. This is the "hidden upstream buffering" from README_UPDATES.md §1, measured.
3. **Most of the data is discarded.** The streamer allows one SBS message per aircraft per second, of *any* type. Position, velocity and identity messages compete for that one slot, so only about 1 in 6 transmitted positions is stored, at every load level. That is why the map's position is about 2 s old on average and up to about 12.5 s old at p99, and why it is off by hundreds of metres. Turning aircraft make it worse.
4. **Throughput is not the old system's problem.** At 6,000 aircraft (24,200 frames/s) the streamer used 25% of one core, the web server 19%, and readsb 6%. There was no backlog: the database median was 67 ms in the first quarter of the run and 66 ms in the last. Its weaknesses are latency and data loss, not capacity.
5. **No stalls.** The worst one-second window in any run had a database median of 811 ms, at 50 aircraft, where the batch timer dominates. An earlier sweep showed one 5-second pause, but it hit readsb and the feeder at the same moment and did not recur here, so it was the Docker VM, not the old pipeline.
6. **The committed schema is incomplete.** `ads-b-receiver/schema.sql` does not create `aircraft_position_history`, which the streamer writes and the server reads. A fresh deployment from the repository fails every batch insert. The harness adds the table from PROJECT_REPORT.md.
7. **Decoders agree.** On identical input, readsb and the new C++ decoder both match ground truth on 100% of positions and altitudes, and agree on 100% of callsigns and squawks. The new decoder reports about 8% more positions than readsb's SBS output (1,017,606 against 941,906 at 6,000 aircraft). That has not been investigated yet; readsb likely applies extra validation or suppresses some SBS position output.

## Rerunning

```bash
bench/legacy/run.sh
```

The default sweep is 50, 200, 1,000 and 3,000 aircraft and takes about 20 minutes. Add the 6,000 run with `SCENARIOS="50 200 1000 3000 6000"`. Each run's raw logs are deleted after analysis, so the disk stays clean. Run it on the benchmark host for the final report's before/after table.
