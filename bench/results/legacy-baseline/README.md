# Fall 2025 Baseline: Findings

The full tables are in [report.md](report.md), generated by [`bench/legacy/`](../../legacy/) (method and caveats in its README). Each run fed 120 s of synthetic traffic in real time to the **unmodified** Fall 2025 pipeline: readsb → Python streamer → Postgres → Node API → map polling every 2 s.

> **Machine:** Apple M2 laptop, Docker Desktop Linux VM, local Postgres (no Supabase network hop). Latencies are therefore a lower bound on the deployed system. CPU use and the load ceiling must be re-measured on the benchmark host. The latency *structure* comes from the code's design and does not depend on the machine.

## Headline numbers (median across 50–3,000 aircraft)

| Measure | Fall 2025 system |
|---|---|
| Frame received → visible on the map | **≈ 1.1–1.6 s** median, **2–4.6 s** p99 |
| Positions that ever reach the database | **17%** (5 of every 6 position reports are discarded) |
| Age of the position the map shows | **≈ 2 s** median, **≈ 12.5 s** p99 |
| Distance between the map and the aircraft's real position | **≈ 460–530 m** median, **≈ 2.7 km** p99 (in the browser) |
| Database and API correctness | Every shown position matched a real transmitted position (0 unmatched) |

For context, the new C++ pipeline takes the same frames from received to track state updated in **about 1 µs** median, keeping every position. Its publisher, gateway and map are not built yet, so that is not yet an end-to-end comparison.

## What the measurements show

1. **The latency is designed in.** Almost all of it comes from three waits in the code, not from slow computation:
   - the streamer's 1 s batch flush (or 100 buffered aircraft, whichever comes first);
   - the database round trip;
   - the map's 2 s poll, which alone adds about 1 s on average and 2 s at worst.

   The database is reached in 81–567 ms median, and the browser poll then adds about another second on average.
2. **Load shortens latency.** The database median falls from 567 ms with 50 aircraft to 81 ms with 3,000. That is because the batch of 100 aircraft fills sooner, not because anything got faster. readsb behaves the same way: its output buffer flushes at 1,280 bytes or 50 ms, so its median drops from 27 ms to 2 ms. This is the "hidden upstream buffering" from README_UPDATES.md §1, measured.
3. **Most of the data is discarded.** The streamer allows one SBS message per aircraft per second, of *any* type. Position, velocity and identity messages compete for that one slot, so only about 1 in 6 transmitted positions is stored. That is why the map's position is about 2 s old on average and up to about 12 s old at p99, and why it is off by hundreds of metres. Turning aircraft make it worse.
4. **Throughput is not the old system's problem.** At 3,000 aircraft (12,100 frames/s) the streamer used 22% of one core and showed no backlog (latency in the first and last quarter of the run was 79 and 82 ms). Its weaknesses are latency and data loss, not capacity. A 6,000-aircraft run was attempted but aborted when the laptop ran out of disk space.
5. **One stall in the 1,000-aircraft run.** For about 5 s at t ≈ 72 s, the database median rose to 3.4 s. readsb's output stalled at the same moment (its p99 jumped to 1.5 s) and the feeder ran 280 ms late, so this was the whole system pausing, most likely the Docker VM, rather than the old pipeline. The benchmark host rerun will show whether it recurs.
6. **The committed schema is incomplete.** `ads-b-receiver/schema.sql` does not create `aircraft_position_history`, which the streamer writes and the server reads. A fresh deployment from the repository fails every batch insert. The harness adds the table from PROJECT_REPORT.md.
7. **Decoders agree.** On identical input, readsb and the new C++ decoder both match ground truth on 100% of positions and altitudes, and agree on 100% of callsigns and squawks. The new decoder reports about 8% more positions than readsb's SBS output. That has not been investigated yet; readsb likely applies extra validation or suppresses some SBS position output.
