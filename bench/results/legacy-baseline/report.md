# Before / After: Measured Results

Generated by `bench/legacy/run.sh`. The same synthetic traffic is played through readsb in real time, once through the Fall 2025 pipeline as delivered (git tag `fall2025-final`: Python streamer → Postgres → Node API → 2 s map poll) and once through the new pipeline (`adsb-live` → multicast feed → `adsb-gateway` → WebSocket push). Every position shown is matched to the transmitted frame it came from using the generator's ground truth. Method and caveats: [bench/legacy/README.md](../../legacy/README.md).

Environment: Linux 6.10.14-linuxkit, 8 CPUs (Docker), Python 3.12.3, Node v18.19.1, readsb version: 3.16.21 wiedehopf git: v3.16.21 (committed: Sun Nov 1 12:57:32 2026 0000). 120 s of traffic per run, seed 2025, repo `f572366`. The first 20 s of each run are excluded as warm-up.

> **Host stalls detected; tail percentiles (p99 and above) are unreliable for:** 50 aircraft (12.1 ms), 200 aircraft (2.9 ms), 1,000 aircraft (8.5 ms), 3,000 aircraft (24.7 ms). The check: the new pipeline's core, replayed from a file with nothing to wait on, released frames late by that much at p99 (threshold 1 ms; a quiet host gives a few µs). That means the host paused the container, which inflates the tails of both systems. Medians are robust to this. Rerun on a quiet machine or the benchmark host for tail numbers.

## Notes

- **Lower bound on the real system:** Postgres runs locally, not on Supabase across the internet, so production latencies were higher.
- **Browser columns:** estimates. Fall 2025: the measured API latency plus the map's uniformly distributed 0–2 s poll wait. New: the measured WebSocket arrival plus a uniform 0–100 ms render wait and one animation frame. Rendering itself is not included for either.
- **Both systems include readsb** (standing in for dump1090 / the receiver), and its default output buffering adds tens of milliseconds to everything downstream of it. The new pipeline's own demodulator (Workstream A) will remove that stage.
- **CPU of the new pipeline:** `adsb-live`'s track-state thread spins on its input queue instead of sleeping (lowest latency, as in a feed handler), so it uses one full core even when traffic is light. The Fall 2025 processes sleep between batches.
- **Probe resolution:** the database and API probes poll every 100 ms, which adds about 50 ms on average. The WebSocket probe timestamps each frame on arrival.
- **Laptop numbers:** CPU and the throughput limit depend on the machine. Rerun on the benchmark host for the final report.
- **readsb output buffering:** defaults, as on a stock receiver: `--net-json-port=<ports> TCP json position output listen port / TCP server, sends one line with a json object containing aircraft details for every position received (default: 0) (consider raising --net-ro-size to 8192 for less fragmentation if this is a concern) --net-ro-size=<size> TCP output flush size (maximum amount of internally buffered data before writing to network) (default: 1280) --net-ro-interval=<seconds> TCP output flush interval in seconds (maximum delay between placing data in the output buffer and sending)(default: 0.05, valid values 0.0 - 1.0) --net-ro-interval-beast-reduce=<seconds> TCP output flush interval in seconds for beast-reduce outputs (default: value from --net-ro-interval, valid values 0.0 - 1.0)`
